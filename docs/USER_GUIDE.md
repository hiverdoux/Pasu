# Pasu 사용자 안내서

Pasu는 개인키를 다른 프로그램에 넘기지 않고 SSH 서명을 대신 처리합니다. 관리 앱에서 키를 만들고 사용 규칙을 정하며, 백그라운드 서비스인 agent가 실제 서명을 수행합니다.

이 안내서는 서명된 앱의 설치와 사용을 설명합니다. 소스에서 개발용 프로그램을 빌드하거나 서명 앱을 제작하려면 [빌드 안내서](BUILDING.md)를 참고하세요.

## 앱 설치

### 준비물

- macOS 27과 로그인한 사용자 계정.
- 관리자 인증을 처리할 수 있는 계정.
- 서명된 `Pasu.app`과 같은 버전의 소스 폴더. 설치 스크립트가 이 폴더에 있습니다.

완성된 앱을 설치할 때는 Go·Xcode·개발자 인증서가 필요하지 않습니다. 현재 공개 다운로드 파일은 제공하지 않으므로, 아래 절차는 신뢰할 수 있는 경로에서 해당 앱을 확보한 경우에 사용할 수 있습니다.

### 설치와 시작

다른 개발자가 자신의 인증서로 만든 앱의 신규 설치 기능은 구현되어 있지만 실제 다른 팀의 유효한 인증서로 시험하지 못했습니다. 앱은 한 번에 하나를 설치·사용합니다. 다른 제작자로 전환해도 각 제작자의 자료는 별도로 보존합니다.

1. 소스 폴더의 `dist/Pasu.app`에 앱을 놓습니다.
2. Pasu 관리 앱이 열려 있다면 종료합니다.
3. 터미널에서 소스 폴더로 이동해 다음을 실행합니다. 스크립트 전체를 `sudo`로 실행하지 마세요. 필요한 파일 교체 단계에서 관리자 인증을 요청합니다.

```sh
./scripts/launchd.sh verify-app
./scripts/launchd.sh install
```

앱을 다른 폴더에 두려면 `PASU_CANDIDATE_APP` 환경 변수로 해당 `Pasu.app`의 경로를 지정할 수 있습니다.

설치 중 승인 대기 또는 `requiresApproval`이 표시되면 macOS의 백그라운드 실행 승인이 필요합니다. 시스템 설정 → 일반 → 로그인 항목 및 확장 프로그램에서 Pasu를 허용하고 다음을 실행합니다.

```sh
./scripts/launchd.sh start
```

`./scripts/launchd.sh status`로 정상 실행을 확인한 뒤 설치된 `/Applications/Pasu.app`을 엽니다. 처음 설치해 키 목록이 비어 있는 것은 정상입니다. 소스 폴더는 업데이트·복원·삭제 명령에 필요하므로 보관하세요.

인터넷으로 받은 앱은 macOS의 실행 확인을 거칩니다. 이 프로젝트의 빌드 스크립트는 Apple 공증을 수행하지 않으므로, 실행이 차단되면 제공자에게 서명·공증 상태를 확인하세요. [Apple의 앱 실행 안내](https://support.apple.com/en-us/102445)를 참고하세요.

### 서명 앱을 직접 제작하려면

개발용 빌드와 실제 키를 사용할 서명 앱은 요구 조건이 다릅니다. 자신의 Developer ID 인증서와 프로파일을 설정해 앱을 만들 수 있습니다. 다만 다른 개발자 팀의 유효한 인증서를 사용한 실제 서명·신규 설치·업데이트 시험은 아직 하지 못했습니다. [서명 앱 제작](BUILDING.md#서명-앱-제작)의 조건과 명령을 확인하세요. 완성된 앱은 위 설치 절차로 설치합니다.

## 자료 폴더

키·로그 파일은 `~/.ssh/pasu/profiles/<제작자 ID>/`에 저장합니다. 제작자 ID는 서명 팀 ID와 앱 식별자를 점으로 연결한 값입니다. 예: `ABCDE12345.org.example.pasu`. 키 목록·설정·규칙과 키를 여는 암호는 해당 제작자의 Keychain 접근 그룹에 보관합니다.

제작자를 전환해도 이 자료는 삭제하거나 다른 제작자에게 옮기지 않습니다. SSH가 연결하는 `~/.ssh/pasu/agent.sock`은 현재 실행 중인 Pasu가 공통으로 사용합니다. SSH 설정의 `IdentityFile`에는 **현재 제작자의 공개키 파일 경로**를 넣으세요. 관리 앱의 폴더 버튼으로 해당 파일을 찾을 수 있습니다.

구형 앱을 처음 업데이트하면 기존 파일을 제작자 폴더로 옮깁니다. 이때 `IdentityFile` 경로를 한 번 변경해야 합니다. 기존 앱으로 복원하면 파일도 원래 위치로 돌아가므로 그 경로를 다시 사용합니다. SSH 설정은 자동 변경하지 않습니다.

구형 앱을 이미 제거해 기존 폴더의 자료만 남았다면, 이전 제작자의 구형 앱을 복원한 뒤 업데이트하세요. 설치본 없이 자료의 제작자를 추측해 분류하지 않습니다.

## 키 만들기

1. 사이드바의 `+` 또는 `⌘N`을 누릅니다.
2. 키 이름과 passphrase를 입력하고 인증 방식을 선택합니다.
3. Touch ID 또는 로그인 암호로 저장을 확인합니다.

passphrase는 개인키 파일을 암호화하는 별도 암호입니다. 최소 16바이트(영문 16자 분량)가 필요하며, 여러 무작위 단어처럼 추측하기 어려운 값을 사용하세요. Pasu가 Keychain에 보관하지만 백업 복구를 위해 별도로 안전하게 보관해야 합니다.

키 이름은 1~128바이트이며 기존 이름과 대소문자만 다르게 만들 수 없습니다. 새 키는 활성 상태이고 허용·거부 규칙은 비어 있습니다.

| 인증 방식 | SSH 서명 시 동작 |
|---|---|
| 첫 인증 후 agent 종료까지 | 처음 사용할 때 인증하고, 수동으로 잠그거나 agent가 종료될 때까지 잠금 해제를 유지합니다. |
| 매번 인증 | 서명할 때마다 Touch ID 또는 로그인 암호를 요구합니다. |
| 인증 없음 | 허용된 요청은 사용자 인증 없이 서명합니다. 화면이 잠긴 동안에는 필요한 Keychain 항목을 읽을 수 없습니다. |

`인증 없음`은 서명 보호 수준을 낮춥니다. 어느 방식을 선택해도 키 생성·활성화·이름 및 설정 변경·규칙 삭제·키 삭제에는 인증이 필요합니다. 잠금과 비활성화는 추가 인증 없이 할 수 있습니다.

## 공개키 등록과 SSH 설정

### 공개키를 서버에 등록

키를 선택한 뒤 `개요` 탭의 `공개키`에서 복사 버튼을 누릅니다. 화면에서 줄여 보이는 부분도 복사할 때는 원문 전체가 포함됩니다. 폴더 버튼은 Finder에서 `key.pub` 파일을 보여 줍니다.

기존 SSH 접속이나 서버 관리 콘솔을 사용해, 복사한 공개키 한 줄을 원격 계정의 `~/.ssh/authorized_keys`에 추가합니다. 같은 폴더의 `key`는 암호화된 개인키이므로 서버에 올리지 마세요. 새 키로 접속되는 것을 확인할 때까지 기존 관리 방법을 유지하세요.

### 사용할 키 지정

다음 예시를 `~/.ssh/config`에 추가합니다. `HostName`은 서버 주소, `User`는 서버 계정 이름으로 바꿉니다. `IdentityFile`에는 Pasu의 폴더 버튼으로 찾은 `key.pub`의 경로를 넣습니다. Finder에서 해당 파일을 선택하고 `⌥⌘C`를 누르면 경로를 복사할 수 있습니다. Pasu의 공개키 복사 버튼은 경로가 아닌 공개키 내용 한 줄을 복사합니다.

```sshconfig
Host example-pasu
    HostName example.test
    User sample
    IdentityAgent ~/.ssh/pasu/agent.sock
    IdentityFile ~/.ssh/pasu/profiles/<제작자 ID>/keys/<uuid>/key.pub
    IdentitiesOnly yes
    ForwardAgent no
    AddKeysToAgent no
    UseKeychain no
```

`IdentityAgent`는 서명을 맡길 Pasu 소켓, `IdentityFile`은 사용할 공개키를 지정합니다. `IdentitiesOnly yes`로 키를 제한하면 다른 키까지 차례로 시도해 승인창이 여러 번 뜨는 것을 줄일 수 있습니다. `ForwardAgent no`는 원격 서버에서 Pasu를 다시 사용하는 전달 기능을 끕니다.

설정 결과를 확인합니다. 아래 명령은 서버에 SSH 연결을 시도하지 않습니다.

```sh
ssh -G example-pasu | grep -E '^(identityagent|identityfile|identitiesonly|forwardagent) '
./scripts/doctor.sh example-pasu '~/.ssh/pasu/profiles/<제작자 ID>/keys/<uuid>/key.pub'
```

기존 `Host`·`Match` 설정에 따라 공개키 지정이 누적될 수 있으므로, 출력에 의도한 키 하나가 선택되는지 확인하세요. Pasu는 SSH 설정과 서버의 공개키 등록을 자동 변경하지 않습니다.

## 첫 연결과 승인

```sh
ssh example-pasu
```

처음 보는 요청에는 승인창이 나타납니다. 키 이름·지문과 `책임 프로세스 > 최하위 프로세스`를 확인하세요. 예를 들어 `터미널 > ssh`는 터미널에서 시작된 실행 계보의 `ssh`가 직접 서명을 요청했다는 뜻입니다.

- **책임 프로세스**: macOS의 프로세스 관리자인 `launchd` 바로 아래에 있는 프로그램입니다.
- **최하위 프로세스**: Pasu에 직접 서명을 요청한 프로그램입니다.
- **프로세스 사슬**: 직접 요청한 프로그램에서 부모를 따라 `launchd`까지 올라간 실행 계보입니다.

| 선택 | 결과 |
|---|---|
| 이 사슬 항상 허용 | 현재 사슬을 규칙으로 저장해 이후 일치하는 요청을 자동 허용합니다. |
| 이번만 허용 | 현재 요청만 허용하며 규칙을 저장하지 않습니다. |
| 이 사슬 항상 거부 | 현재 사슬을 규칙으로 저장해 이후 일치하는 요청을 거부합니다. |

화면의 프로그램과 요청이 예상한 것인지 확인한 뒤 선택하세요. 사슬에 코드 서명을 신뢰할 수 없는 프로그램이 있으면 `이 사슬 항상 허용`은 사용할 수 없습니다.

항상 허용 규칙은 필요한 인증과 실제 서명, 마지막 사슬 검사가 성공한 뒤 저장됩니다. 인증을 취소하거나 요청 도중 사슬이 바뀌면 저장되지 않습니다. 항상 거부 규칙은 선택 후 저장합니다.

## 키와 규칙 관리

### 활성 상태와 잠금

`활성` 스위치를 끄면 그 키는 SSH 키 목록에서 빠지고 서명 요청도 거부합니다. 다음 사용을 허용하려면 다시 활성화하세요.

`첫 인증 후 agent 종료까지` 방식에서는 자물쇠 버튼으로 잠그거나 미리 잠금 해제할 수 있습니다. **잠금은 사용 중단과 다릅니다.** 활성 키가 잠겨 있으면 다음 허용 요청이나 처음 보는 요청에서 다시 인증할 수 있습니다. 사용을 막으려면 비활성화하세요.

키 이름과 인증 방식은 `개요`에서 바꿉니다. 이름을 바꾸어도 키의 고유 식별값·지문·서버에 등록된 공개키 본체는 유지됩니다. 공개키 끝의 설명은 `pasu-<이름>`으로 바뀝니다. 인증 방식을 바꾸면 이전 인증 결과를 재사용하지 않습니다.

관리 앱의 마지막 창을 닫아도 agent와 잠금 해제된 키는 유지됩니다. agent까지 종료하려면 소스 폴더에서 다음을 실행합니다.

```sh
./scripts/launchd.sh stop
```

### 사슬 검사 방식

키의 `개요`에서 규칙의 비교 범위를 선택합니다.

| 방식 | 규칙 적용 조건 |
|---|---|
| 전체 사슬 검사(기본값) | 모든 구성원의 실행 경로·사용자 ID·코드 서명 신원·순서와 터미널 상태가 같아야 합니다. |
| 책임 프로세스만 | 책임 프로세스의 실행 경로·사용자 ID·코드 서명 신원만 같으면 됩니다. 중간 프로그램이나 터미널 상태는 비교하지 않습니다. |

`책임 프로세스만`은 허용·거부 규칙 모두의 적용 범위를 넓힙니다. 예를 들어 같은 터미널 앱에서 다른 중간 도구로 요청해도 같은 규칙이 적용될 수 있습니다. 허용과 거부가 함께 일치하면 거부가 우선합니다.

변경에는 사용자 인증이 필요하며 진행 중인 요청이 끝난 뒤 적용됩니다. 저장된 전체 사슬과 잠금 해제 상태는 유지됩니다. 어느 방식이든 새 영구 허용을 저장할 때의 전체 코드 서명 검사와 요청 도중의 사슬 변경 검사는 수행합니다.

터미널의 `포그라운드` 표시는 요청 프로그램이 터미널의 포그라운드 작업 그룹에 속했다는 뜻입니다. 사람이 직접 입력했다는 증거는 아닙니다.

### 저장된 규칙

`규칙` 탭에서 허용·거부 목록을 확인합니다. 펼치면 전체 사슬, 코드 서명 신원과 생성·사용 시각을 볼 수 있습니다. 규칙 삭제에는 사용자 인증이 필요합니다. 삭제 후에는 다른 일치 규칙을 적용하며, 남은 규칙이 없으면 다음 요청에서 다시 묻습니다.

프로그램이 업데이트되어도 경로와 코드 서명 신원이 유지되면 기존 규칙을 사용할 수 있습니다. 실행 구조가 달라져 현재 검사 조건을 충족하지 않으면 새 요청으로 처리합니다.

### 접근 기록

키의 `기록` 탭은 해당 키의 최근 기록을, 사이드바의 `개요`는 전체 활동을 보여 줍니다. 기록을 펼치면 원문을 볼 수 있습니다.

로그 파일은 `~/.ssh/pasu/profiles/<제작자 ID>/pasu.log`이며, 기본 5MiB 한도에서 이전 파일 하나를 `pasu.log.old`로 보관합니다. 개인키와 passphrase는 기록하지 않지만 키 이름·지문·프로그램 경로가 포함되므로 공유 전에 확인하세요.

## 키 삭제와 백업

### 키 삭제

`개요` 맨 아래의 `이 키 삭제…`를 누르고 확인합니다. Pasu는 키를 비활성화하고 진행 중인 서명이 끝나기를 기다린 뒤 사용자 인증을 요청합니다. 성공하면 암호화된 키 파일을 휴지통으로 옮기고 키별 Keychain 항목과 목록 정보를 삭제합니다. 실패하거나 취소한 경우 키가 비활성 상태로 남을 수 있으므로 화면에서 확인하세요.

서버에 등록한 공개키는 별도로 제거해야 합니다. 다른 관리 경로로 접속해 해당 `authorized_keys`의 정확한 공개키 한 줄만 삭제하세요. 기존 SSH 연결은 로컬 키 삭제만으로 종료되지 않습니다.

휴지통의 파일은 passphrase로 암호화되어 있습니다. 필요 없으면 해당 파일을 정리하세요. 파일 삭제가 저장장치의 물리적 완전 소거를 보장하지는 않습니다.

### 백업과 복구 한계

| 항목 | 보관 방법 |
|---|---|
| `~/.ssh/pasu/profiles/<제작자 ID>/keys/<uuid>/key` | 암호화된 개인키입니다. 안전한 별도 위치에 백업합니다. |
| 같은 폴더의 `key.pub` | 서버 등록과 지문 확인에 사용할 수 있도록 함께 보관합니다. |
| 키별 passphrase | 개인키 백업과 분리해 안전하게 보관합니다. |

현재 버전에는 일반 키 가져오기·내보내기 화면이 없으며, 다른 Mac에서 백업을 Pasu로 자동 복구하는 기능도 없습니다. Mac을 사용할 수 없을 때를 대비해 서버의 별도 관리 경로를 유지하세요.

## 업데이트와 이전 설치 복원

### 일반 업데이트

기존 앱과 같은 서명 팀·앱 식별자로 만든 새 버전을 사용합니다. 다른 제작자나 앱 식별자로 바꾸려면 아래의 [제작자 전환](#제작자-전환)을 따릅니다. 다른 개발자 팀으로 만든 앱의 실제 업데이트와 복원은 아직 검증하지 못했습니다.

1. 현재 키와 규칙이 정상인지 확인하고 진행 중인 서명 작업을 마무리합니다.
2. 이전 설치 백업인 `.rollback`이 남아 있으면, 현재 설치의 정상 동작을 확인한 뒤 같은 버전의 소스 폴더에서 `./scripts/launchd.sh finalize`로 정리합니다.
3. 새 버전의 서명 앱과 같은 버전의 소스 폴더를 준비합니다. 관리 앱을 종료하고 다음을 실행합니다.

```sh
./scripts/launchd.sh verify-app
./scripts/launchd.sh install
```

4. 백그라운드 실행 승인을 요청하면 설치 때와 같이 허용하고 `./scripts/launchd.sh start`를 실행합니다. `./scripts/launchd.sh status`로 확인합니다.
5. 구형 자료 폴더를 처음 이전했다면 SSH 설정의 `IdentityFile`을 현재 제작자의 공개키 경로로 변경합니다. 관리 앱의 폴더 버튼으로 파일을 찾고 Finder에서 `⌥⌘C`로 경로를 복사할 수 있습니다. 관리 앱에서 버전·키·규칙·설정을 확인하고 실제 인증과 SSH 연결을 시험합니다.
6. 정상 동작을 확인한 뒤 이전 설치 백업을 정리합니다.

```sh
./scripts/launchd.sh finalize
```

업데이트는 키와 규칙을 유지하지만 agent를 재시작하므로 기존 잠금 해제 상태는 끝납니다. 설치 성공만으로 백업이 자동 삭제되지는 않습니다.

## 제작자 전환

전환할 제작자의 서명된 `Pasu.app`과 같은 버전의 소스 폴더를 준비합니다. 다시 사용할 제작자의 앱도 보관하거나 나중에 같은 제작자에게서 확보할 수 있어야 합니다. 자료 보존만으로 앱 자체가 보관되는 것은 아닙니다.

1. 관리 앱을 닫고 진행 중인 SSH 서명을 마무리합니다. 이전 설치 백업이 남아 있으면 먼저 정상 동작을 확인하고 `finalize`로 정리하거나 `rollback`으로 복원합니다.
2. 소스 폴더의 `dist/Pasu.app`에 전환할 앱을 놓고 실행합니다.

```sh
./scripts/launchd.sh verify-app
./scripts/launchd.sh install --switch-developer
```

3. 백그라운드 실행 승인을 요청하면 허용하고 `./scripts/launchd.sh start`를 실행합니다.
4. `./scripts/launchd.sh status`와 관리 앱에서 현재 제작자의 자료를 확인합니다. 처음 사용하는 제작자라면 키 목록이 비어 있는 것이 정상입니다. 이전 제작자의 키와 규칙은 그 제작자의 자료에 그대로 남습니다.
5. 현재 제작자의 공개키 경로로 SSH 설정을 바꾸고 연결을 확인합니다. 정상 동작을 확인한 뒤 `./scripts/launchd.sh finalize`로 이전 **앱 백업만** 정리합니다.

직전 앱으로 돌아갈 때는 아래의 `rollback`을 사용합니다. 그 백업을 정리한 뒤 다른 제작자로 돌아가려면 해당 제작자의 앱을 준비하고 위 전환 절차를 다시 실행합니다. 같은 서명 팀·앱 식별자가 유지되면 보존된 자료를 다시 사용합니다. 인증서를 갱신해도 팀과 앱 식별자는 유지해야 합니다.

실제 다른 개발자 팀의 인증서로 전환·복원·재설치를 검증하지는 못했습니다. 자동 검사는 합성 서명·Keychain·서비스 응답을 사용하며 실제 환경 검증을 대신하지 않습니다.

### 실패 시 복원

`.new`는 설치 도중 준비한 앱, `.rollback`은 이전 설치의 백업입니다. 오류가 나면 출력된 단계와 이 파일들의 상태를 확인하세요. 이전 앱 백업이 있다면 관리 앱을 종료한 뒤 다음을 실행할 수 있습니다.

```sh
./scripts/launchd.sh rollback
```

복원된 버전과 같은 소스 폴더에서 `./scripts/launchd.sh status`로 확인합니다. 최초 설치처럼 백업이 없거나 `finalize`로 백업을 지운 경우에는 이 명령으로 복원할 수 없습니다. 백업 없이 `.new`만 남은 경우 `./scripts/launchd.sh cleanup`으로 준비 파일을 정리한 뒤 다시 설치합니다. 사용자 자료는 삭제하지 않습니다. 복원에 실패하면 남은 백업을 보존하세요.

사슬 검사 설정을 모르는 구버전으로 돌아가려면, 복원 전에 현재 앱에서 모든 키를 `전체 사슬 검사`로 바꾸어야 합니다. Keychain 접근 그룹을 바꾼 업데이트는 아래 이전용 앱도 복원에 필요합니다.

## 구버전에서 이전

### v1 키를 v2로 복사

기존 v1 키와 설정을 발견하면 관리 앱이 이전을 제안합니다. `Touch ID로 이전`을 선택하면 기존 키와 설정을 인증·검증하고 `기존 Pasu 키`라는 새 항목으로 복사합니다. 기존 허용 목록은 옮기지 않으며 첫 요청에서 새 규칙을 정합니다. 기존 파일과 Keychain 항목은 자동 삭제하지 않습니다.

취소하거나 실패하면 원인을 확인한 뒤 다시 시도할 수 있습니다. 복사한 키로 실제 SSH 연결을 확인하기 전에는 기존 자료를 제거하지 마세요.

v1 자료를 정리하려면 agent를 중지하고 아래 명령을 실행합니다. 확인 창과 사용자 인증 뒤 v1 Keychain 항목인 `ssh-key-unlock-v1`만 삭제합니다.

```sh
./scripts/launchd.sh stop
/Applications/Pasu.app/Contents/Library/LoginItems/PasuAgent.app/Contents/MacOS/pasu -remove-legacy-keychain
```

이후 현재 제작자 자료 폴더에 남은 v1의 `key`, `key.pub`, `pasu.conf`, `approvals.conf`, `conf.hmac` 등 남은 파일을 확인해 정리하고 `./scripts/launchd.sh start`로 다시 시작합니다. v2의 `keys/` 폴더는 유지하세요.

### v2.1.1에서 v2.2로 이전

이전용 서명 앱을 `dist/migration/Pasu.app`, 최종 앱을 `dist/Pasu.app`에 준비합니다. 같은 버전의 소스 폴더가 필요합니다. 직접 제작할 수 있는 조건과 명령은 [구버전 이전용 앱 제작](BUILDING.md#구버전-이전용-앱-제작)에 있습니다.

관리 앱을 종료하고 진행 중인 SSH 서명을 마무리한 뒤 실행합니다.

```sh
./scripts/launchd.sh install --migrate
```

스크립트가 agent를 중지하고 Keychain 접근 그룹과 앱을 전환하며, 기존 파일을 제작자별 자료 폴더로 옮깁니다. 요청된 사용자 인증과 백그라운드 실행 승인을 처리한 뒤 SSH 설정의 `IdentityFile`을 새 공개키 경로로 변경하세요. 관리 앱의 폴더 버튼으로 파일을 찾고 Finder에서 `⌥⌘C`로 경로를 복사할 수 있습니다. 이후 키·규칙·인증·SSH 연결과 로그인 후 자동 실행을 확인하세요.

정상 동작을 확인하면 `./scripts/launchd.sh finalize`로 백업을 정리합니다. 그 전까지는 이전용 앱과 `.rollback` 백업을 함께 보관하세요. 실패 시에는 `./scripts/launchd.sh rollback`으로 그룹·이전 앱·자료 경로를 복원하고, `IdentityFile`도 원래 경로로 되돌립니다. SSH 설정은 자동 변경하지 않습니다.

## 앱 제거

### 키 자료를 보관하고 앱만 제거

관리 앱을 종료하고 소스 폴더에서 실행합니다.

```sh
./scripts/launchd.sh uninstall
```

agent와 자동 실행 등록, 앱을 제거합니다. 모든 제작자의 Keychain 항목과 자료 폴더, 서버의 공개키와 별도 설치 백업은 남습니다. 같은 제작자의 앱을 다시 설치하면 보존된 자료를 사용합니다. 설치 백업이 남아 있다면 재설치 전에 `rollback` 또는 정상 설치 후 `finalize`로 정리해야 합니다.

### 키도 삭제하고 사용 중단

1. 새 SSH 서명 요청을 중단하고 필요한 기존 연결을 마무리합니다.
2. agent가 실행 중인 상태에서 키를 비활성화하고, 제거할 공개키와 서버 목록을 확인합니다.
3. 다른 관리 경로를 확보한 뒤 서버에서 해당 공개키를 제거하고 로컬 SSH 설정의 Pasu 참조를 정리합니다.
4. agent를 유지한 채 관리 앱에서 키를 하나씩 삭제합니다. 실패한 키가 있으면 먼저 원인을 해결합니다.
5. v1 항목이 남아 있다면 위의 v1 정리 절차를 완료합니다. 관리 앱을 닫고 `./scripts/launchd.sh uninstall`을 실행합니다.
6. 필요한 백업을 남긴 뒤 잔여 로그·설정·휴지통의 키 파일과 필요 없는 설치 백업을 확인해 정리합니다.

모든 키를 지워도 Keychain의 빈 관리 항목 `registry-v2`는 남으며, 이를 삭제하는 전용 명령은 없습니다. `uninstall`도 사용자 자료를 완전히 지우는 명령은 아닙니다.

## 문제 해결

`./scripts/launchd.sh status`는 앱 서명·파일 소유권·키 목록과 실행 상태를 검사합니다. 출력의 `repository`, `installed`, `START`는 각각 소스, 설치된 agent, 최근 시작 기록의 버전이며 같은 버전이어야 합니다.

| 증상 | 확인할 내용 |
|---|---|
| `Permission denied (publickey)` | agent 실행 상태, SSH 설정의 공개키 경로, 서버의 공개키 등록을 확인합니다. |
| 승인창이 나타나지 않음 | 키 활성 상태와 거부 규칙, `pasu.log`를 확인합니다. `ASK-V2 result=timeout`은 취소·무응답·실행 오류 등에 공통으로 쓰이므로, `ASK-V2 detail`의 `err`도 확인합니다. |
| 승인창이 다시 나타남 | 규칙이 저장되었는지, 실행 경로·프로그램 구성·터미널 상태가 바뀌었는지 확인합니다. |
| 항상 허용 버튼 비활성 | 사슬에 코드 서명이 미검증인 프로그램이 있습니다. 이번 요청을 허용하거나 거부할 수 있습니다. |
| Touch ID 대신 로그인 암호를 요구함 | 두 방법 모두 지원하는 정상 인증 동작입니다. |
| SSH 때 인증창이 나타나지 않음 | 이미 잠금 해제된 키인지, `인증 없음` 방식인지 확인합니다. |
| `status`·설치 검사에서 Keychain 접근 불가 또는 `-25308` 오류 | 화면 잠금을 해제하고 다시 시도합니다. 계속 실패하면 Keychain 접근 상태를 확인합니다. 이 오류만으로 자료 손상이나 보호 설정 오류라고 판단할 수는 없습니다. |
| 자료 폴더 소유권·권한 오류 | 표시된 경로가 본인 소유의 실제 폴더인지 확인합니다. `~/.ssh/pasu`, 그 아래 `profiles`와 제작자 폴더는 권한 `700`(소유자만 접근)이 필요합니다. 소유권과 경로를 확인한 폴더에만 `chmod 700 "폴더 경로"`를 적용하세요. 앱은 기존 권한을 자동 변경하지 않습니다. |
| 관리 앱이 연결되지 않음 | agent 실행 상태와 관리 화면의 오류를 확인합니다. 앱 복사본이나 개발용 임시 서명 앱은 설치된 agent에 연결할 수 없습니다. |
| 제작자 전환 후 예전 키가 보이지 않음 | 현재 제작자의 키만 표시됩니다. 예전 제작자의 앱으로 돌아가면 그 제작자의 자료를 다시 사용할 수 있습니다. |
| `-34018` 또는 배포 앱 실행 제한 오류 | 제공자에게 agent의 서명·프로파일·Keychain 권한을 확인하도록 요청합니다. 직접 빌드했다면 [서명 문제 해결](BUILDING.md#서명-문제-해결)을 참고하세요. |
| 관리 앱과 agent의 버전이 다름 | 같은 버전의 앱으로 다시 설치합니다. |
| 키 삭제 뒤에도 서버 접속 가능 | 서버의 공개키 등록과 이미 열려 있는 SSH 연결을 확인합니다. |

## 용어

- **SSH 키·서명**: 서버가 사용자를 확인하는 개인키·공개키 쌍과, 개인키를 가진 사실을 증명하는 계산 결과입니다.
- **지문·UUID**: 각각 공개키를 요약한 확인값과 Pasu가 키에 부여하는 고유 식별값입니다.
- **Keychain**: macOS의 보안 저장소입니다. Pasu의 키를 여는 암호와 관리 정보를 보관합니다.
- **코드 서명 신원**: 프로그램의 서명에서 확인한 제작자와 앱 식별 정보입니다.
- **소켓**: SSH나 관리 앱이 agent와 통신하는 로컬 연결 지점입니다.
- **TTY**: 터미널 상태입니다. 포그라운드는 터미널이 입력 대상으로 지정한 작업 그룹, 백그라운드는 그 밖의 작업 그룹입니다. 제어 터미널이 없는 요청도 있습니다.
- **rollback / finalize**: 이전 설치 복원과, 확인이 끝난 이전 설치 백업 삭제 명령입니다.
